## Two Lean programs, and why Lean

Kalari ships two executables, both Lean 4 natives:

- <RepoLink path="Kalari/Main.lean">kalari</RepoLink> is the main service on the VM. It serves the MCP endpoint, runs the gate, drives the run pipeline, and keeps the evidence store.
- <RepoLink path="Aashaan/">kalari-aashaan</RepoLink> is the supervisor inside each microVM. It runs the untrusted job, enforces the time and output caps, and prints one JSON verdict.

Lean carries the containment logic as theorems checked at build time. A broken proof fails `lake build`, so the binary cannot ship with a weaker gate. The supervisor imports `Std` only, never the compiler library, so it stays a small static binary that starts inside each guest. State this plainly: the proofs cover the gate decision and the aashaan caps. They do not cover the agent generated code or the sandbox backend.

## The gate and its four theorems

Every `run_in_sandbox` call passes the gate decision before it reaches any backend. It returns allow or refuse with a named reason. Four theorems pin what allow means:

- Workspace: keeps writes inside the workspace. Absolute paths and `..` segments must resolve under it on a segment boundary. See <RepoLink path="Kalari/Gate.lean">decide_workspace in Kalari/Gate.lean</RepoLink>.
- Network: keeps network use inside the allowlist. Each requested host and port must match an entry exactly. See <RepoLink path="Kalari/Gate.lean">decide_network in Kalari/Gate.lean</RepoLink>.
- Caps: keeps all three caps within the configured maximum. Time, output bytes, and memory each compare within bounds. See <RepoLink path="Kalari/Gate.lean">decide_caps in Kalari/Gate.lean</RepoLink>.
- Secrets: keeps secrets out of the call. No non-empty secret may appear in the workspace or any argument. See <RepoLink path="Kalari/Gate.lean">decide_secrets in Kalari/Gate.lean</RepoLink>.

A fifth check refuses 32-character alphanumeric runs, the shape of a pasted key. A refusal never reaches `msb`.

## A run, step by step

1. The gate checks the call. A refusal stops here.
2. Kalari resolves each allowed hostname to IPs.
3. `msb create` starts a fresh guest with `--no-net` plus one allow rule per API.
4. Kalari copies the workspace and the aashaan into the guest. It sets `vm.overcommit_memory=1` there first.
5. `msb exec` runs `kalari-aashaan` with the timeout, the output cap, and the command. The job starts with an empty environment and an explicit `PATH`.
6. The aashaan reports one verdict: `exited` with an exit code, `killed_timeout`, or `killed_output_cap`.
7. The trusted checks run in fresh guests: the candidate truth check and the differential against v1. The artifact must sit at the workspace root. Exploratory commands without an artifact report `passed=false`.
8. The verdict and logs go to the evidence store. Teardown stops and removes the guest.

The <DocLink to="containment/">Containment</DocLink> runs are the worked example. They show both the crash path and the kill path with measured timings.

## The five tools

The tool schemas and the request handler live in one file, so schema and routing cannot drift. See <RepoLink path="Kalari/Mcp.lean">Kalari/Mcp.lean</RepoLink>.

- `what_changed` lists the changes between two specs with stable change IDs. It calls Vimanam as a subprocess.
- `blast_radius` finds the callers, tests, and earlier decisions each change touches. Statuses stay per ID: searched, not searchable, or unknown. Links go to Lambo.
- `recall_lessons` returns lessons for change kinds as checks that must pass. Lookup walks from the change kind.
- `run_in_sandbox` runs the proved gate, then a throwaway microVM run, and returns the verdict with logs.
- `record_lesson` stores what a verified run showed. A failure needs Clef to attribute it to the API change. A verified pass stores the observed behaviour directly.

## Memory

Kalari is Lambo single writer. OpenCode never talks to Lambo directly. Lessons key by change kind, such as `pagination_changed`. Recall walks from the change kind to the lesson, not through recall ranking. The measured limit is honest: the frozen runs published zero lessons, so memory showed no benefit there. Read <DocLink to="evidence/">Evidence and limits</DocLink> for what that means.

## Judgement calls

Clef answers three fixed questions on Vultr Inference at the System One endpoint. Its answers are a model opinion, logged with probabilities. They never enter the gate and never decide the verdict. The web app labels them as opinion everywhere they appear.

## Security boundaries

- No key enters any guest. Keys stay in environment names in config, and values stay on the host.
- Each run gets its own network policy from the gate. The reference setup instead lets the agent choose, and it once chose none.
- `--no-net` denies default egress and ingress. The TLS domain rule limitation is real on msb 0.7.13, so Kalari resolves hostnames on the host and passes IP rules.
- Caddy terminates TLS. SSH reaches the VM over Tailscale only. The firewall group opens only ports 80 and 443.

## Deployment

The Vultr preset lives in <RepoLink path="deploy/vultr/README.md">deploy/vultr/README.md</RepoLink>. One VX1 VM holds `kalari serve`, Lambo, the evidence API, Caddy, and the microVM fleet. Systemd units carry `UMask=0022`, which Microsandbox storage requires. The key travels to the VM over SSH stdin only. The generic local preset lives in <RepoLink path="deploy/local/README.md">deploy/local/README.md</RepoLink> with a Docker backend for hosts without KVM. The line holds: runs on Vultr, and anywhere else you point it.

## Dependencies

Each entry names its version, how Kalari invokes it, and why, from <RepoLink path="docs/architecture.md">docs/architecture.md</RepoLink>:

- Lean 4.35.0 with `Std`: the executables and the proofs.
- Vimanam 2.1.0 as a CLI subprocess: change facts across OpenAPI, GraphQL, and protobuf.
- Lambo as a `lambo serve` child process over MCP: lessons, links, and canonization.
- Microsandbox `msb` as a CLI subprocess: microVMs with their own kernel and a network policy.
- `curl` as a subprocess: outbound HTTPS, since Lean has no HTTP client or TLS.
- Caddy in front of `kalari`: automatic HTTPS.
- Chaaya in `web/`: the read-only front end.
