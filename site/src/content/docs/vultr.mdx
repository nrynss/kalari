Everything Kalari needs runs on Vultr, under one account. Cloud Compute provides one VM with KVM exposed, and that VM hosts `kalari serve`, Lambo, the read-only evidence API, the observer and its per-run broker, and every Microsandbox microVM — nested virtualisation, guests inside the rented guest. Serverless Inference provides one OpenAI-compatible endpoint that serves the coding models, the judgement calls, and the embeddings behind recall. Untrusted code runs in real microVMs next to the models that wrote it, with no second provider in the loop.

The demonstrated host shape is measured in <RepoLink path="dev-diary/research/vultr-vm.md">research/vultr-vm.md</RepoLink>: the VX1 plan with 2 vCPU (AMD, `svm`), 8 GB RAM, and 120 GB disk at $0.076 an hour, Ubuntu 24.04, IPv4 only. KVM is proven on the host, not assumed: `/dev/kvm` present, the `svm` CPU flag, and `msb doctor` passing, per <RepoLink path="dev-diary/research/sandbox.md">research/sandbox.md</RepoLink>.

What ran at once: 102 user-path sessions on the one VM, back to back, each against API microVMs with per-run sandboxes alongside. Each API service runs in its own microVM with egress denied and its port published on the VM public address, per the proved route in <RepoLink path="bench/README.md">bench/README.md</RepoLink>. Each session runs its candidate, baseline, and checks in fresh per-run microVMs through Kalari per-run broker, with its own network policy from the gate. The 102 repeat rows record the VM public address as their API base with live and grading ports, and per-run containment policies, in `slides/data/results.json` with its `repeats-table.txt` aggregate.

The public interface lives at [kalari.nryn.dev](https://kalari.nryn.dev/). These docs live under its `/docs/` path.

## What Vultr runs

| Service | Responsibility |
|---|---|
| Cloud Compute | Hosts Kalari, Lambo, the evidence API, the observer and broker, and the microVMs |
| Serverless Inference | Serves the coding models, Clef, and embedding requests |
| Firewall | Allows public HTTP and HTTPS while SSH stays on Tailscale |
| Caddy on the VM | Obtains certificates and serves the interface and docs |

Microsandbox is a tool installed on the VM. It is not a separate Vultr sandbox service: Vultr has no sandbox product of its own, and its agent sandboxing guide uses Microsandbox, per <RepoLink path="dev-diary/research/sandbox.md">research/sandbox.md</RepoLink>.

The demonstrated host uses Ubuntu 24.04 with 2 vCPU and 8 GB RAM. Check KVM availability before deploying.

Model requests leave the host for Serverless Inference. Consumer execution and artifact comparison run on the VM.

## Prepare the machine

Create an Ubuntu host with virtualization exposed. Connect through your own SSH alias.

The examples use `kalari` as that alias. It represents your host, username, and SSH authentication settings.

```sh
ssh kalari 'uname -m; test -r /dev/kvm && test -w /dev/kvm'
ssh kalari 'command -v sudo; command -v python3'
```

The operator needs sudo on the target. The installer creates a separate `kalari` service user and grants that user KVM access.

Keep SSH restricted to your management network. Point an A record for your chosen hostname at the VM.

Allow inbound TCP 80 and 443 through both the Vultr firewall and the host firewall. Caddy needs a publicly resolvable hostname for automatic HTTPS.

The checked-in Caddy configuration uses `kalari.nryn.dev`. Change both hostnames in your deployment copy before using another domain.

## Configure inference

Create your own Serverless Inference access and retrieve its inference key. The account API key and inference key have different purposes.

Kalari uses these endpoint shapes.

| Work | Endpoint | Demonstrated models |
|---|---|---|
| Coding agent | `https://api.vultrinference.com/v1` | DeepSeek V4.1 Flash, GLM 5.3 Flash, Qwen3.8 27B, MiMo V2.6 Flash, Muse Glimmer 30B |
| Decision calls | `https://api.vultrinference.com/v1/systemone` | `clef` |
| Lambo embeddings | Configured from `https://api.vultrinference.com` | `qwen3-embedding-4b`, 2560 dimensions |

Switching model is one config string: the repeats ran the same harness and arms with only the model id changed between projects, across all five ids above. The agent model belongs to the agent's configuration. The service configuration carries the Clef settings and the Lambo child configuration.

List prices per 1M tokens, input / output: DeepSeek V4.1 Flash $0.15 / $0.60, GLM 5.3 Flash $0.10 / $0.35, Qwen3.8 27B $0.15 / $1.00, Clef $0.10 in with no output tokens, Qwen3 Embedding 4B $0.05 — all per <RepoLink path="dev-diary/research/vultr-inference.md">research/vultr-inference.md</RepoLink>. MiMo V2.6 Flash $0.10 / $0.25 and Muse Glimmer 30B $0.25 / $1.00 are from the [Vultr models and pricing page](https://api.vultrinference.com/docs/models), not the research file.

Cost accounting follows the same rule in both arms: the `/v1/usage` delta per session times list price, with cached input at full price. The usage deltas matched OpenCode's own step tokens on the measured probe in <RepoLink path="dev-diary/research/coding-agent.md">research/coding-agent.md</RepoLink>. Totals from the 0.2.3 repeat rows: 102 sessions cost about $5.62 at list price (Kalari arm $1.53 over 51 sessions, alone $4.09 over 51).

Production validation requires the shown Clef endpoint and model. Check model access on your own inference account.

[Serverless Inference documentation](https://api.vultrinference.com/docs) · [Endpoint reference](https://api.vultrinference.com/docs/reference).

## Install the deployment

Run the deployment installer from a source checkout on your operator machine. It builds the executables on the VM against that host's libraries.

The operator machine needs SSH, rsync, curl, and access to the inference key. A docs build also needs Node.js and Chrome or Chromium.

Clone the source and review the deployment script.

```sh
git clone https://github.com/nrynss/kalari.git
cd kalari
less deploy/vultr/install.sh
```

Load your inference key through the operator environment. The demonstrated keyring entry is:

```sh
export VULTR_INFERENCE_API_KEY="$(secret-tool lookup service vultr-inference account kalari)"
test -n "$VULTR_INFERENCE_API_KEY"
./deploy/vultr/install.sh --host kalari --source "$PWD"
unset VULTR_INFERENCE_API_KEY
```

Use your own secret manager if that keyring entry does not exist. The installer sends the key through SSH stdin.

The VM receives a mode-0600 environment file owned by the service user. The key never appears in the unit's command line.

The installer also builds these docs for `/docs/`. It installs Caddy, Lambo, service definitions, static assets, and the read-only API.

The default session is an idle deployment example. Configure real specifications, workspaces, and a baseline command before connecting an agent.

## Files on the VM

| Path | Contents |
|---|---|
| `/opt/kalari/bin/` | Kalari executables and Lambo |
| `/etc/kalari/kalari.json` | Host policy and endpoints |
| `/etc/kalari/session.json` | Session paths and baseline command |
| `/etc/kalari/lambo.toml` | Lambo storage and embedding settings |
| `/etc/kalari/kalari.env` | Protected inference environment |
| `/var/lib/kalari/evidence/.kalari/evidence.jsonl` | Append-only evidence |
| `/var/lib/kalari/lambo.db` | Graph store |
| `/srv/kalari/www/` | Static judges' interface |
| `/srv/kalari/www/docs/` | Built documentation |

The read-only API listens on loopback from `kalari serve`. Caddy routes `/api/*` to that service.

The web interface reads stored evidence. A fresh installation does not contain the demo's published benchmark records.

## Restart and verify

An install refreshes files. Explicitly restart the running services when replacing binaries.

```sh
ssh kalari 'sudo systemctl restart kalari caddy'
ssh kalari 'sudo systemctl is-active caddy kalari'
ssh kalari '/opt/kalari/bin/kalari --version'
```

Expect two `active` lines and the installed release version. Check HTTPS from outside the management network.

```sh
curl -fsS -o /dev/null -w 'site %{http_code}\n' https://kalari.nryn.dev/
curl -fsS -o /dev/null -w 'docs %{http_code}\n' https://kalari.nryn.dev/docs/
curl -fsS -o /dev/null -w 'runs %{http_code}\n' https://kalari.nryn.dev/api/runs
```

Replace the hostname when deploying your own instance.

## Connect an agent on the VM

The systemd MCP service keeps a process running. It does not expose an HTTP MCP endpoint.

A coding agent normally launches its own stdio server using its own session configuration. Run the agent on the host containing its candidate workspace.

```sh
kalari serve /absolute/path/to/kalari.json /absolute/path/to/session.json
```

The <DocLink to="mcp/">MCP guide</DocLink> shows OpenCode configuration and direct discovery. Give separate sessions separate evidence and workspace directories.

## Publish docs without replacing the service

Build the documentation with the Vultr base. Keep the source checkout as the working directory.

```sh
cd site
npm ci --no-audit --no-fund
ASTRO_SITE=https://kalari.nryn.dev ASTRO_BASE=/docs npm run build
npm run check -- dist
python3 scripts/links.py dist --base /docs
rsync -az --delete dist/ kalari:kalari-docs/
ssh kalari 'sudo rsync -a --delete "$HOME/kalari-docs/" /srv/kalari/www/docs/'
```

Install rsync on the target before this command. The command replaces only the published docs directory.

Caddy serves the updated static files without a restart. Keep the interface, service binaries, and evidence store outside this sync target.

## Troubleshooting

Inspect unit logs without printing the credential file.

```sh
ssh kalari 'sudo journalctl -u kalari -u caddy -n 80 --no-pager'
ssh kalari 'sudo systemctl status kalari caddy --no-pager'
```

| Symptom | Check |
|---|---|
| Certificate issuance fails | Public DNS and inbound 80/443 |
| HTTPS works but `/api/runs` fails | `kalari` status and Caddy proxy |
| MCP exits during startup | Config paths, service permissions, and credential variable |
| Sandbox creation fails | KVM access, image cache, and storage permissions |
| Docs assets return 404 | Rebuild with `ASTRO_BASE=/docs` |
| GitHub Pages links appear on the VM | Deploy the Vultr build rather than the Pages output |
| Docs work but migration cannot run | Configure the session separately from web hosting |
