## Method

The comparison runs six conditions across two upgrades. The frozen pair is payouts B1 plus B2 plus B4 plus B5, then settlements B1 plus B2 plus B3 plus B5. <RepoLink path="bench/FROZEN.md">bench/FROZEN.md</RepoLink> pins the commit and every hash. Both arms use the same OpenCode 2 with the same DeepSeek V4.1 Flash on Vultr Serverless Inference. Only Kalari differs between arms.

Five repeats run per condition. Each session caps at 20 minutes. An HTTP retry inside one consumer process never counts as a sandbox run. Cost multiplies input tokens by 0.15 USD per million and output tokens by 0.60 USD per million, with cached input at full price. Both arms use the same rule.

## What is measured

The table on the <DocLink to="judges/">Judges walkthrough</DocLink> reports cost, sandbox runs, wall time, stuck time, containment, verdicts, and right-first-time counts. Every figure traces to one of 60 row files under `bench/runs/kalari/` and `bench/runs/reference/`. The <RepoLink path="bench/RESULTS.md">traceability script in bench/RESULTS.md</RepoLink> recomputes every aggregate from those files, including the zero-lesson count for those frozen rows, plus the token basis, byte-identical provenance, and clean cleanup.

Those frozen rows ran on an earlier build whose production validation refused the observer configuration, so they carry zero published lessons. Read that count as history about those rows, never as a limit now.

## What is not claimed

Learned memory showed no benefit in the frozen comparison because no lesson existed to recall. The showcase scenario is manufactured and labeled as such. Its docs are true sentence by sentence, but the behaviour combination is synthetic. Five repeats per condition is a small sample. Condition 1 and condition 6 match condition 5 on verdicts, so the measured edge is cost, attempts, and containment, not pass rate.
