Deliberate containment demonstration · not a benchmark session

A broken consumer, stopped by its time limit.

Kalari ran a consumer with a known bug on purpose. It follows the page cursor and never stops. It ran in a fresh microVM through the same run_in_sandbox path the agent uses, and the aashaan killed it at the cap this run was given. This is apart from the benchmark: no session in the frozen comparison was stopped by a cap.

The failure

Configured time cap 5,000 ms
Measured wall time 5,007 ms
The verdict Stopped by the time cap killed_timeout · passed is false

The supervisor checks the clock by polling, so the measured time can run past the cap. No fixed overshoot bound is promised. The candidate was killed. The baseline guest was never started, because the candidate wrote no output, and the differential check failed. The run page has the exact detail.

Output cap 65,536 bytes and memory 512 MiB are configuration only. Neither fired in this run.

The boundary

Requested: no network, plus one allow rule for the one API port. Effective, read back from msb inspect right after create: default egress deny, default ingress deny, one rule. Observed: a probe in a second guest created with the same arguments and the same allowlist asked for these.

  • A different port on that same host: refused
  • The host's own SSH port: refused
  • The cloud metadata address: refused
  • A public internet address: refused
  • The one API port the allowlist names: answered, as the rule allows

Every request the allowlist does not name was refused (four of four). The probe is a separate guest, so this is evidence about the configuration, not about the guest that ran the consumer.

The cleanup

This test created two sandboxes. After the run, none of them were still listed, no child process of the run remained (none), and the four sandboxes that existed before were present and unchanged.

These are observed restrictions for the listed requests, from one guest configuration. This is not a claim of zero blast radius.
