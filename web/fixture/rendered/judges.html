What Kalari is

A rehearsal arena for API upgrades.

Kalari plugs into the coding agent you already use over MCP and rehearses an API upgrade in a contained arena. It works out what changed and what it touches. It runs the new code in a throwaway microVM against the real API, with the old version as the reference. It records what the run proved.

The agent writes the code, and Kalari decides what has to be checked and whether it passed.

Filmed and measured on Kalari 0.2.3 with OpenCode 2.2.5. Every figure on this page links to the run or the row behind it.

The problem

Alone, the agent called verify, reported verified, and shipped the wrong amounts.

OpenCode alone with GLM 5.3 Flash called POST /v2/verify on disbursements. The agent reported verified. It shipped 23 payments with the wrong amount. The hidden grader failed the run: 23 changed.

This was not one bad run. Alone, disbursements failed for GLM 5 of 5, for DeepSeek 4 of 5, and for MiMo 2 of 5.

The filmed session is the user-path take. The repeats behind it are the five GLM disbursements sessions alone, all failed, each with 23 mismatched records. Representative row: reference-disbursements-be0c0bfd

Three models, five repeats, forty-five sessions per arm.

Containment on Kalari 0.2.3

The consumer that never stops is still stopped.

One consumer never stops. The aashaan stopped it with killed_timeout, passed is false, at 5,007 ms against a 5,000 ms cap, after 68 pages with 1 wait for one Retry-After.

The boundary probe answered 1 allowed and refused 4 refused: the other port on the same host, the host SSH port, the metadata address and the internet. 0 sandboxes and 0 processes were left behind.

  • allowed: answered
  • other-port-same-host: refused
  • host-ssh: refused
  • metadata-link-local: refused
  • internet: refused

The supervisor watches by polling, so the measured time can pass the cap. No fixed overshoot is promised. The output and memory caps are configuration only.

Requested: no network plus one allow rule for the grading API port. Effective, read back from msb inspect: default egress deny and default ingress deny, with that one rule. Observed: the probe answered the allowed port and refused the other four targets. The probe ran in a second guest with the same arguments, not inside the consumer guest.

This is not a benchmark session. Verified cleanup: the run removed both sandboxes it created and left the pre-existing API sandboxes unchanged. This is an observed restriction, not a claim of zero blast radius.

The earlier baseline

The frozen benchmark stays, demoted.

Sixty sessions with DeepSeek V4.1 Flash: $0.019 against $0.082 per session. The frozen runs published no lesson, so they could not show what memory adds.

The repeats contradict the idea that memory adds nothing: every payouts repeat wrote a lesson and the later upgrades recalled it. And DeepSeek does not verify on its own: alone it passed the easier upgrades and failed disbursements in four of five sessions.
